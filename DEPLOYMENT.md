# Deploy Gym Logger on Render

One free Node web service serves the built React app and Express API over HTTPS. PostgreSQL stays in your existing Supabase project. No custom domain is needed.

## Separate repositories

Keep the existing GitHub repositories:

- Backend: `https://github.com/reinisvaravs/gym_logger_backend`
- Frontend: `https://github.com/reinisvaravs/gym_logger_frontend`

Render connects to the **backend repository only**. Its build script compiles the backend, clones the frontend's `main` branch into the ignored `.render/frontend` directory, installs its locked dependencies, and builds React there. Express serves `.render/frontend/dist` and `/api` from the same origin. No repository merge or second Render service is needed.

The frontend repository must be public for the unauthenticated clone. Do not put a GitHub token in its URL. If you make it private later, this build approach needs authenticated repository access configured separately.

## Create the service

First push the replacement frontend commit, then the backend commit, so the backend build can fetch the prepared frontend.

In Render choose **New → Blueprint**, connect `gym_logger_backend`, and use its `render.yaml`. It specifies the Free plan and generates a session secret. Supply your database host, user, and password when prompted.

For manual setup choose **New → Web Service**, connect `gym_logger_backend`, and use:

| Setting | Value |
| --- | --- |
| Runtime | Node |
| Root Directory | Leave empty (this repository is already the backend) |
| Plan | Free |
| Build Command | `npm run build:render` |
| Start Command | `npm start` |
| Health Check Path | `/health` |
| Node version | `24.20.0` |

Manual setup also requires the environment variables below. Use a region near your database. The ignored `.env.render` file contains your prepared values for Render's **Environment → Add from .env**; do not commit that file.

## Deploying updates

Backend pushes trigger Render's linked-repository deployment when auto-deploy is enabled. A frontend-only push does **not** trigger it: after pushing frontend changes, use **Manual Deploy → Deploy latest commit** on the same Render service. Every build fetches the current frontend branch and logs its commit SHA. A backend rollback may fetch a newer frontend, so select a compatible frontend branch before rebuilding older backend code.

You can override `FRONTEND_REPO_URL` and `FRONTEND_BRANCH` in Render; defaults are the frontend URL above and `main`. Both are already in the Blueprint. Frontend changes require no changes to backend Git history.

For a local production-build check, run `npm run build:render` inside `backend/`. This fetches the remote frontend, not your uncommitted local frontend changes. For a normal development session, continue running `npm run dev` separately in each repository.

## Environment variables

Set these in Render, never in frontend code or committed `.env` files:

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `NODE_VERSION` | `24.20.0` |
| `SESSION_SECRET` | Generated by the Blueprint, or a private random secret of at least 32 characters |
| `DB_HOST` | Supabase session-pooler host from the project's Connect dialog |
| `DB_PORT` | Session-pooler port, usually `5432`; use the displayed value |
| `DB_NAME` | `postgres`, unless your database uses another name |
| `DB_USER` | Exact session-pooler username, including the project suffix |
| `DB_PASSWORD` | Database password |
| `DB_SSL_CA` | Optional trusted root certificate PEM if the connection requires it |

For a manual session secret, generate one locally with `node -e "console.log(require('node:crypto').randomBytes(48).toString('hex'))"` and paste the output into Render. Keep it unchanged across redeployments to preserve existing sessions.

Production always uses verified TLS for PostgreSQL. The public Supabase Root 2021 CA is included in `certs/supabase-ca.crt` alongside Node’s built-in trusted roots. This is a public certificate, not a secret. If your provider changes certificates or uses a different private CA, supply its root certificate in `DB_SSL_CA`; do not disable verification. Literal `\n` separators in the PEM are supported. For local PostgreSQL, TLS remains optional through `DB_SSL=true`.

Use the Supabase **session pooler** for IPv4 connectivity. Copy all values from the Connect dialog rather than mixing direct and pooler credentials. The application pool is limited to five connections. Keep the existing schema; `database.sql` is a reference and deployment does not execute it. The session store creates its `session` table if missing, so the database user must have permission to do so. That table contains sensitive session data: verify it is not accessible through Supabase's public Data API (disable that API if unused, or restrict access/RLS in your project).

Render supplies `PORT` and `RENDER_EXTERNAL_URL`. The latter is used as the trusted frontend origin automatically. Leave `FRONTEND_URL` unset on Render unless using a custom domain; then set it to the exact HTTPS origin, without a trailing slash. Do not copy the local `http://localhost:5173` value into Render.

No `VITE_API_URL` setting is needed for production: the frontend calls `/api` on its own origin. API routes are `/api/users/login`, `/api/me`, `/api/training-types`, etc. Local development retains the existing unprefixed routes and separate Vite server. `/health` remains unprefixed in both environments.

## Verify the public deployment

1. Open `https://YOUR-SERVICE.onrender.com/health`; expect JSON with `status: "OK"`.
2. Open the app, register a disposable account, and log in. Check that the `gym.sid` cookie is Secure, HttpOnly, and SameSite=Lax.
3. Refresh `/history`, `/calendar`, and a session detail URL directly; the app should load without a 404 and stay signed in.
4. Create a training type, log a session, edit a set, and verify the calendar and history. Check both themes and units.
5. Log out, then open `/api/me`; expect `401`. Modifying requests with an untrusted or missing Origin should return `403`.
6. Confirm the browser sends API calls to this same HTTPS domain, with no localhost requests or mixed-content warnings.

The server checks database connectivity before listening. A failed connection makes the deployment fail instead of advertising a working app. `/health` checks the running process, not ongoing database availability. Unexpected errors are logged on the server and return generic JSON to clients. Auth rate limits use memory and reset on restart; this configuration is intended for one service instance.

Free Render web services sleep after 15 minutes without incoming traffic. The first visit can take about a minute to wake the app. Add a brief note next to the portfolio link so employers know to wait. Database free-tier quotas and inactivity policies also apply; check project availability before sharing the link.
